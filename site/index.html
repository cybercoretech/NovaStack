        // 05 · install

        From zero to a running backend.

        Five steps. Copy each block into a terminal.

        1. 1Check the requirements

          You need Rust — or newer (install or update with rustup). Docker is optional: generated projects use it for a local Postgres and docker compose.

          terminal
          rustup update stable
rustc --version

        2. 2Install NovaStack

          Install it from crates.io, then let novastack doctor check your toolchain (rustc, cargo, git, docker, sqlx, just).

          terminal
          cargo install novastack
novastack --version
novastack doctor

        3. 3Create a project

          Run novastack new with no arguments for an interactive wizard, or pass flags:

          terminal
          novastack new my-api --db postgres --plugins auth --no-interactive
          flagwhat it does
          -t, --templatethe template (default rest)
          --dbpostgres (default), sqlite or none
          --pluginscomma-separated, e.g. auth,otel,redis,workers
          --dry-runlist the files it would write, write nothing
          --outparent directory (default: current directory)

        4. 4Run it

          Copy the example environment, start Postgres, and run. (With --db sqlite or none, skip the docker compose line.)

          terminal
          cd my-api
cp .env.example .env
sed -i "s/^JWT_SECRET=.*/JWT_SECRET=$(openssl rand -hex 32)/" .env   # auth only
docker compose up -d db
cargo run

          In a second terminal:

          terminal
          curl localhost:8080/health
# {"status":"ok","version":"0.1.0"}

        5. 5Grow it

          Add plugins and components as you go. Run these inside the project directory.

          terminal
          novastack add redis                 # add a plugin later
novastack generate handler orders   # new component, routed at /orders
novastack list                      # templates, plugins and databases

        // 06 · status

        What's not there yet.

        NovaStack is early (—). These gaps are known and tracked:

        • Plugins guard HTTP only. The auth plugin protects HTTP routes; there's no gRPC interceptor or WebSocket authentication yet.
        • The login handler is a stub. Generated /auth/login issues a token for any non-empty credentials and is clearly marked; wire it to your user store.
        • Metrics, not tracing export. The otel plugin serves Prometheus metrics; OpenTelemetry trace export is planned.
        • In-memory examples. The example resources in the REST and HTMX templates keep data in memory, so they work with any database choice.
